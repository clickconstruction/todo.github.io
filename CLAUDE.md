# CLAUDE.md

Guidance for Claude working in this repo. See README.md for what the app is and how to run it.

## Product rules (don't break these)

- **Nothing the user made is deleted.** Actions are completed or dropped, projects are completed or dropped, tags are dropped or put on hold, and everything else they keep (folders, places, people and their groups, events, calendars, attachments, perspectives) is archived. Database triggers and RLS enforce this; never add a delete path for any of it. Only links and device settings are removed outright: tag links, "waits for" links, a person's place on a project, reminders on an item, push subscriptions, API tokens and approved senders.
- **The MCP can do everything a user can,** except manage API tokens and approved email senders, which stay app-only for security. What belongs to one device rather than the account (its push subscription, Focus, which sidebar groups are collapsed) is set in the app on that device. Subscribed calendars are the `calendars` tool and the Settings page is the `settings` tool; a calendar's private link can be saved through the MCP but is never returned.
- **Planned vs Due:** Planned is an intention; Due is only for hard deadlines. Flagged means "important now".
- **The database is the source of truth for rules.** Put a rule in a trigger or SQL function when it must hold for both the app and the MCP, and test it in `supabase/tests/`.

## Stack

- Plain JavaScript ES modules, no framework and no build step. State lives in `db` and `app` in `js/state.js`.
- Supabase project `cgssdelgtxlrfgozchps` (Postgres with owner-only RLS on every table). Apply migrations with the Supabase MCP (`apply_migration`) or with `python3 dev/sbq.py supabase/migrations/<file>.sql` (the Management API with the CLI's saved login; then record the version in `supabase_migrations.schema_migrations`), and keep a copy in `supabase/migrations/`. Never `supabase db push`: the history table holds the MCP's own version numbers. `python3 dev/sbq.py supabase/tests/<file>.sql` runs a rule test.
- MCP server: a Cloudflare Worker in `mcp/`, at `https://mcp.todotooling.com/mcp`. It uses the server secret key, so **every query must be scoped to the token owner** (`api.u` / `user_id`).
- Local Node is v20, so deploy with `npx -y wrangler@3 deploy`.

## Every release

1. Bump `VERSION` in `sw.js` when any shell file changes (the service worker is cache-first). Add new JS files to the `SHELL` list.
2. Run the tests that apply:
   - `node mcp/test.mjs` for MCP changes (it also counts requests per call)
   - the smoke suites at `http://localhost:8765/?mock`: `const { run } = await import('/dev/smoke.js'); await run({ only: ['suite'] })`
     The full run takes about six minutes, longer than the Browser pane's 45-second script timeout. A timed-out call keeps running in the page, and a second run resets the mock data under it, which produces dozens of bogus `null.click` failures. In the Browser pane start it detached and poll: `import('/dev/smoke.js').then(m => m.run()).then(r => window.__smokeResult = r)`, then read `window.__smokeResult`. Reload the page before any re-run. Run them at desktop width (1280 wide): in a narrow Browser pane the app is in phone layout and the sidebar suite fails two checks for pinned perspectives. In a suite, press a picker row with `tap()` (pointerdown, then pointerup on whatever is under the finger), never a bare pointerdown: a press that never lifts holds Full Review's `redraw()`, and every later suite that waits for a live update fails. Blur before a suite ends when it closed a sheet with focus in a field (a hidden Browser pane draws no frame to move it), or the next suite's keys read as typing. When files change under the running server (an edit, a merge), the pane may import a cached copy of `dev/smoke.js` or a module and run the old checks: refetch the changed files first (`fetch(url, { cache: 'reload' })`), then reload, and make sure the total matches the suite's check count.
   - SQL rule tests: wrap them in a transaction that rolls back (or ends by raising an exception) so nothing is left behind in the real database
3. Apply any new migration and deploy the Worker (if `mcp/` changed) as part of finishing the feature; Todd has asked for this to happen without a separate go-ahead once the tests pass. Migration first: the app and the Worker read new tables on start. Then commit, push, and fast-forward `main` (that deploys the app) in the same go: Todd's standing instruction is "always commit, push, merge".
4. Commit messages: an app release is titled after the feature with the version in parentheses, matching `sw.js` (`Steps type and "Waits for" links (v74)`). Worker-only changes are prefixed `MCP:` and carry no version; test-only changes are prefixed `smoke:` or `dev:`.

## MCP limits (Cloudflare free plan)

Each call gets **50 outgoing requests** and **about 10 ms of CPU**, and the library is large (8,000+ open tasks).

- Never make one request per item. Batch with `id=in.(…)`.
- Whole-library reads come from one snapshot, `rpc/mcp_snapshot`. If you add a column to `tasks`, add it to `mcp_snapshot`. The mirror in `mcp/test.mjs` takes its columns from the test rows, so give a test task the new column or the tests won't see it.
- "What's available" comes from `rpc/available_task_ids`. Keep the SQL, `js/availability.js` and the MCP's `availabilityOf` / `parkedOf` in sync.
- Reads are cached per call (`api.q`); writes clear the cache.
- REST paging adds `order=id.asc`; tables without an `id` column need an entry in `TIE` in `mcp/src/index.js`.

## Gotchas

- `_config.yml`'s Jekyll `exclude` is a prefix match: keep the trailing slashes (`supabase/`, not `supabase`), or `supabase-client.js` disappears from the site.
- `config.js` is committed and holds only the public publishable key. Never put a secret key in it. Local overrides go in `config.local.js` (gitignored, localhost only).
- In SQL, `only` is a reserved word; don't use it as a parameter name.
- View submit handlers (`gtdSubmit`, `sheetsSubmit` and the rest, called from the `submit` listener in `js/main.js`) are plain functions, never `async`: return false when the form isn't theirs, otherwise call `e.preventDefault()` at once, start the save without awaiting it, and return true. A Promise is truthy and stops the chain, and a `preventDefault()` after an `await` comes too late, so the browser submits the form and the page navigates away (v142).
- Live updates never redraw under the user. Full Review and Six each have their own `redraw()`: Full Review waits while a press is held, a decision is saving or a row is open for editing; Six waits while a sheet is open or a field has focus and draws once it closes. A live update calls that `redraw()`, never `app.render()` directly, or a press that straddles it loses its click (v128).
- Short questions (a name, a key, an offset) use `ask()` in `js/state.js`, a sheet on `#sheet2` that can sit over an open editor. Never `prompt()`: Safari draws it as a white system box over the dark app.
- Dailies (`tasks.daily`, `daily_ticks`, js/dailies.js, mcp/src/dailies.js): the rules both sides share (which days are asked for, the week, the summary line) live in `js/daily-rules.js`, which has no imports so the Worker can use it. A daily action has no dates or repeat rule (a trigger clears them), is never "available", and is ticked per day; un-ticking sets the tick to `cleared`, it is never deleted. *Have to* (`must`) may show a miss and appears in must-dos; *Should* (`should`) must never nag; *Could* (`could`) is a menu of options folded away at the bottom of Today (no dots, no misses, a count of days this month) and is never asked about. A weekly check is a daily with `every: 'week'` (`tasks.daily = {tier, every: 'week', since}`): `onDay` is never true for it, so it stays out of Today and the Daily review, and the Weekly Review's `checks` step lists it instead. It counts as ticked when it has a tick on or after the day the open weekly review started (today when none is open), so each review starts it fresh; un-ticking clears every tick since then. The step is done without a click once every check is ticked. A monthly check (`every: 'month'`) is listed on the monthly review (`monthlyBody` in js/views/horizons.js), a quarterly check (`every: 'quarter'`) on the quarterly check-in (`quarterlyBody`) and a yearly one (`every: 'year'`) on the yearly review (`yearlyBody`); the Weekly Review's horizons step embeds each while it is due. A check's box is time-based (`CHECKS`, `latestRow`, `checkTicked`, `countingTicks`, `checkLine` in daily-rules.js): its newest done tick must come after the review's "fresh" moment (the open weekly review's `started_at`, else the last one's end; `user_settings.horizons_month_at` / `horizons_quarter_at` / `horizons_year_at` for the others) and be younger than half the cycle (3½, 15, 45, 182 days), after which it lapses on its own. A tick's time is its row's `updated_at` (ticking again bumps it past a done click made the same day), so the app and the Worker compare times, never days. Checks look back `LOOKBACK` (400) days; `js/data.js` and `dailiesFor` load ticks that far. If you change `review_apply`, keep `every` in the `daily` it writes.
- Horizons checkboxes (`js/horizon-text.js`, no imports, shared with the Worker): the purpose and vision text is plain text with a few marks (`#`, `##`, `**`, `*`, `- `), rendered by escaping first and then applying the marks, so nothing typed becomes markup. A line starting with `[ ]` / `[x]` is a checkbox, and the ticks live in the text itself. A trigger clears them when `purpose_read_at` / `vision_read_at` changes; the JS pattern and the SQL pattern must match.
- Tech tree (`tree_links`, `goals.kind`, js/tree-rules.js, js/views/tree.js, mcp/src/tree.js): states and layout come from `js/tree-rules.js` (no imports, shared with the Worker); the database refuses loops and archives removed links. Nothing holds or starts a project, or accepts a link, without the user: the app and the MCP offer and say what would change. A project on hold with no accepted requirement is `held`, never `ready`. A requirement can be a card (`requires_kind = 'task'`); the locked side is only ever a goal or a project, since cards wait on cards through `task_waits`, and a project can't require a card inside itself. A destination with no accepted requirement is `unmapped`, never `open`. A Full Review suggestion can carry `tree` (`{ items, links }`, links by place in `items`, at most 40 items): `review_tree_apply` makes it on Submit and `review_undo` takes it back by dropping and archiving. The review's "lately" comes from `rpc/tree_activity` (one read for every project), because the app only keeps the last day of finished cards.
- People groups and projects (`people_groups`, `people.group_id`, `project_people`; js/gtd.js, js/views/gtd.js `peopleHtml` / `projectPeopleHtml`, mcp/src/gtd.js `people_groups` tool): a person is in one group or none and on any number of projects (with a `role` word). Groups are archived, never deleted; the database trigger files an archived group's people under "no group" (the app's Undo puts them back itself), and refuses a group that isn't the owner's or is archived. `project_people` rows are links and may be removed. The arrangement of the People list (`todo.people.arrange`) is a device setting.
- Per-draw indexes: never scan `db.taskTags`, `db.tasks` or `db.taskWaits` once per task. Tag links come from `tagIndex()` in `js/state.js` (`tagsFor`, `effectiveTagIds` use it) and task structure from `ix()` in `js/availability.js`; both are built once per synchronous pass and dropped on a microtask, so a later pass sees new links without anyone invalidating them. The Tags list once scanned every action and every link for each of 145 tags (eleven billion comparisons, a minute of freeze); the `tagsScale` smoke suite times it with a library that size.
- Loading (`js/data.js` `every`): tables over 1,000 rows are paged. The first page asks for the row count, then the remaining pages are fetched together. Don't go back to one page after another: with 8,000 actions that was ten round trips in a row on every reload. A reload on a Full Review shows the card first (`quickReview`) while the library loads behind it.
- Keep Claude ahead (`review_sessions.draft_ahead`, js/views/fullreview.js, mcp/src/fullreview.js): the app cannot wake Claude, so the box is only a switch that Claude reads in `full_review status` while it loops. "Ahead" is the next 20 pending cards after the current one (`AHEAD` in both files; keep them equal, and no more than `upcoming`'s limit). The app reads the next card fresh when you land on it, so a draft made a moment ago is there without waiting for a live update.
- Six (js/views/six.js, mcp/src/six.js): a day's ranked list is `daily_reviews.focus` (six at most, shared with the Daily review's focus, `MAX_FOCUS`). Carry-over is the database's `six_carry(p_day)` / `six_uncarry(p_day)`: open leftovers of the latest earlier day go to the free places at the top of the day's list once (`carried`, `carried_at`; the day stays marked after an undo, so it isn't redone). The caller plans carried and added cards for that day. Dropped is never done: a dropped card keeps its place with a ✕ and is counted apart, in Six, the Daily review's focus and the MCP's `six` status (`dropped`, `done: false`). `user_settings.six_evening_minutes` is when the view opens on tomorrow. The Add picker is `js/six-picker.js` (places to look come from `matrixBoxes`, the availability rules and `rankNow`; the last place is `localStorage` `todo.six.pick`). When no open card has the typed title, the picker's last row makes one (`typed()` reads the search with `parseCapture`, keeping day words in the title since the list sets the day; `createAndAdd` in js/views/six.js saves it through `capture`, already planned).
- Clarify (`js/views/clarify.js`): `CHOICES` keeps the key order 1–9; `GROUPS` only arranges them in rows, so adding a choice means both. `suggested` files in one press (`saveTask` with the suggestion's project and tags, recorded as `next` for Undo); ⏎ on the choice screen presses it when the user isn't typing. The gain field is the only input on that screen, and keys sleep while it has focus. `c` copies the item for Claude at once and `C` opens the sheet of asks (`clarifyAction` `ask` / `asks`). Inbox suggestions (`tasks.suggestion`, `js/inbox-suggestion.js` with no imports, shared with the Worker; `inbox_suggest` in SQL): Claude writes `{decision (the MCP's names: next_action, done, …), ids and names, note, by: 'agent', at}` through `clarify_item` mode `suggest`, one `rpc/inbox_suggest` call for any number of items, and only ever names projects, tags and people that exist. Pending = no `applied_at` / `resolved_at`. Items with one come first in `clarifyQueue`, but the item on screen stays until it is decided or skipped (`currentId` in `current()`), so a suggestion arriving or being dismissed elsewhere never swaps it out under the user. Submit goes through `applySuggestion`, the same code as the choice it names, writing `applied_at` in the same update where the step is one update (next action, done, trash) and otherwise with `stamp()` right after the step succeeds, over the `resolved_at` the trigger wrote as the item left the Inbox, so a step that fails never leaves a suggestion marked applied. Dismiss writes `resolved_at` and `dismissed: true` (its toast's Undo puts the suggestion back). `COLS` includes `suggestion`, so Undo puts it back pending; a trigger stamps `resolved_at` when the item leaves the Inbox any other way (so nothing stays pending on a clarified item). `DRAFT_PROMPT` is the prompt the screen copies; `list_inbox` answers with `suggested` and `missing` so Claude drafts only what has none. Decision `suggested` in the MCP presses Submit for the user.
- Updates (`js/updates.js`): `tryApply` asks the waiting worker to take over and marks the page `applying` until the reload that follows `controllerchange`. Never let that mark stick: a tap on "Update ready · Reload" or Refresh tries again when the last attempt is over three seconds old, a waiting worker that went `redundant` (replaced by the next release while it waited) is swapped for the one waiting now, and a watchdog six seconds after `SKIP_WAITING` reloads if a newer worker has in fact taken over, else clears the mark and asks whatever is waiting now, taking the button down when nothing is. Two releases minutes apart once left every later attempt swallowed (v158). `__resetUpdates` is for the smoke suite.
- Panel stamps (`stampsHtml` in js/editors): Added and Changed sit directly under the inspector's heading (`taskFieldsHtml` / `projectFieldsHtml` take `inspector: true` to leave the foot line out); the editor sheet keeps its foot line. In `.view-head` the title sits on its baseline and everything beside it is centred on the row.
- Mind sweep (`js/views/sweep.js`, `sweep_prompt` in mcp/src/settings.js): hidden built-in prompts are the ids in `user_settings.trigger_hidden`, the user's own are `trigger_custom`. Whatever hides a prompt sits beside a way to see the hidden ones and bring any back one at a time ("View hidden prompts (n)" beside Hide, and under Edit the prompts); `keepPlace` keeps the user on the prompt they were on when the list changes under them. The MCP's `settings get` names them (`mind_sweep.hidden`) and `sweep_prompt {show}` brings one back. The box goes through `captureLine`, so `#project`, `@tag`, `due`/`plan` and `→ gain` work as in the Inbox box; `captured` entries are `{title, where, tags}` read from the line with `readLine` before the save, so the list under the prompt says where each went without another draw, and `sweptLine` counts the filed ones apart. Every draw replaces the capture box, and `capture()` redraws when its save returns: `sweepHtml` reads the live box's text, caret and focus into `state().box` first and `focusInput` puts them back, so nothing typed or pasted while a save is on its way (or while the app reloads on coming to the front) is thrown away (v162).
- Ask Claude (`js/ask-claude.js`): `askPrompt(task, ask, where)` is the text copied for a card; keep it plain lines, the card's facts first, then `What I want:` and the line about the tools. The sheet sits on `#sheet2` so it can open over an editor. `whereAmI()` names the page from the hash.
- Page search (`js/page-search.js`): the box in every page's `.view-head`, mounted by `render()` after each draw, so its text, scope and focus live in `app.pageSearch` and are put back after the draw (handlers read `S()` fresh, never a captured state). "This page" is a DOM filter: rows are `ROWS` (`li.row`, `.group-row`, `.dv-row`, `.six-row`, …) hidden with `.ps-hide`, headings (`.section-title`, `.po-group`) with nothing left under them too; a new list view needs its row in `ROWS` to be searchable. "Everything" is the Search view's `searchResultsHtml` / `searchCount` drawn in place (`#ps-results`), with `searchServer` for completed and dropped. Scope `auto` is the page when it has matches, else everything; the pills set it. A page with no rows searches everything. The sidebar's Search and the phone's bubble open it (`openPageSearch`); `/` and `s` do too (a view's own keys run first in js/main.js, so on Process Inbox and the Full Review `s` still skips); the Full Review, the print sheets and `#search` get no box (`NO_BOX`).
- Last added (`js/views/added.js`, `list_added` in mcp/src/index.js): how a card came in is `tasks.source` (`app`, `email`, `capture` = the Shortcut, `share`, `mcp`, `template`, `repeat`; an import sets `import_id`), and both sides map it the same way (`SOURCES` there, `WAY` in the Worker). Repeats (`source = 'repeat'`, made by the app when one is finished) are left out unless asked for. A card made within five minutes of its project rides on the project's line (`WITH_PROJECT_MS`); a step whose card is in range rides on the card, whose row counts its steps. Day headings count cards, folded ones included, so they add up to the count line. Closed cards older than the session come from the server once per range (`app.addedCache`, read by `findTask` in js/main.js so their rows open); their check is a mark, not a button (`taskRow` `readOnly`), because the check handler only knows `db.tasks`. `taskRow`'s `lead` puts a view's own words first in the meta line.
- Project names (`projectNamed` / `insertProject` in js/data.js; `resolveProject` / `resolveLiveProject` in the Worker): pickers and the capture line see live projects only (active, on hold). A picker's "+ New project" row and the capture chip go through `insertProject`, which reuses a live namesake, reopens a completed one (the picker's row, via `registerCreator`'s label, and the toast say so) and leaves a dropped one alone. The Worker resolves a name to a live namesake first and refuses to put a card into a completed or dropped project. Five cards once vanished into a completed "Movies" that `insertProject` reused silently (v155). The capture grammar's `unknownProject` is the `#word` no project has: offered (a chip, or the Inbox box's toast action), never made on its own. The chip-less boxes (`captureLine` in js/capture-line.js: the Inbox box and a project's box in js/main.js, and the mind sweep's box) read with `bareDay: false`, so "yes to Thursday" stays as typed.
- Capture shorthand (`js/capture-grammar.js`, no imports): `#project`, `@tag`, `due`/`by` + day word, `plan`/`on` + day word, a bare day word = Planned. A name only counts when a project or tag of that name exists. Tag groups sort lists (`tagGroupChildren` in js/state.js: sort, then created_at, then name; the tag editor and `update_tag position` renumber `tags.sort`); `sortTasks` in js/filter.js and `list_tasks sort_by_tag_group` follow the same order, with a project's tags counting for its cards.
- Events (`events` table, js/events.js, mcp/src/events.js): an all-day event is stored from local midnight of its first day to local midnight *after* its last day (end exclusive, as iCalendar does it), in the user's time zone. The app and the Worker both follow this; the feed emits `VALUE=DATE` for them.

## Process Inbox with the user

When the user asks you to draft, prepare or go through their Inbox (`clarify_item`, `list_inbox`):

- Put a **suggestion** on each item, never the decision itself: `clarify_item` mode `suggest`, every item in one call's `items`, a short `note` saying why, and only projects, tags and people that exist (`list_projects`, `list_tags`, `list_people`; the Worker refuses the rest, and a suggestion never creates anything). They press Submit in Process Inbox, where items with a suggestion come first.
- `list_inbox` says which items still have none (`missing`) and how many have one (`suggested`); draft the missing ones and leave the rest alone. The app's **Copy a prompt** gives them this very ask (`DRAFT_PROMPT` in js/inbox-suggestion.js).
- When they say **"submit"** on an item, call `clarify_item` with decision `suggested` to press it for them. Use mode `do` (an ordinary decision) only when they say "just do it".
- Tell them how many you drafted and which you weren't sure about.

## Full Review with the user

When the user is going through a Full Review (`full_review` tool):

- Turn what they say into a **suggestion** on the current card; they press Submit in the app.
- When they say **"submit"** (for example "submit, next card"), call `full_review` with action `submit` to press it for them. **"Submitted"** means they already pressed it; just check `status`.
- Use `annotate` / `decide` directly only when they say "just do it".
- Name the card in every reply, because they may have moved on in the app. Check `status` before suggesting, so a suggestion never lands on the wrong card.
- **Keep Claude ahead:** when `status` says `draft_ahead.on` (their box in the review's header, or `full_review` action `ahead`), keep a suggestion waiting on each of the next 20 cards without being asked: draft the ids in `draft_ahead.missing` (`upcoming`, then `suggest` with `items`), then check `status` again about every 30 seconds with `/loop` or a scheduled wake-up, and stop when it is off or the review is finished. Never draft on the card they are on unless they ask (they may have dismissed your draft), and never draft drop or done for something they haven't let go of.
